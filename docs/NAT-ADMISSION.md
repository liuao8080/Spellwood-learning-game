# 同一校园网络的身份准入

这是单个权威 Node 服务的应用层候选策略，未部署。它允许一组老师或学生共享 NAT 后开始使用，同时保留新身份、密码工作和请求总量的明确上限。它不是在线人数承诺，也不识别硬件或“同一台设备”。

## 限额

以下令牌桶初始为满，按时间连续补充，补充后不超过突发容量。每次请求同时检查来源地址和整个服务的桶；任何一个不足时都不扣另一个桶的令牌。

| 工作 | 同一直接连接地址：突发 / 持续补充 | 单个服务进程：突发 / 持续补充 |
|---|---|---|
| API 请求和 WebSocket Upgrade 合计 | 400 / 每秒 40 | 1,200 / 每秒 200 |
| 身份 POST 请求 | 360 / 每分钟 180 | 1,200 / 每分钟 600 |
| 创建新游客 | 60 / 每分钟 30 | 180 / 每分钟 90 |
| 注册、登录、恢复和更换恢复码尝试 | 60 / 每分钟 30 | 120 / 每分钟 60 |

密码操作还保留每个“连接地址 + 不区分大小写的用户名”滚动 60 秒最多 8 次的限制；上述四种密码操作共享该记录。旧有注册、登录和恢复的 8 次滚动窗口不变，更换恢复码现在也受此限制。没有按用户名对全网执行统一锁定。失败、成功及格式合法但凭据不正确的尝试都计入；超过用户名窗口的请求不再消耗密码工作桶。

密码服务的生产 scrypt 参数保持 N=32768、r=8、p=3，整个 Node 进程最多同时运行 2 个推导，另有 32 个等待位置。第 35 个尚未完成的推导会返回 PASSWORD_BUSY，而不是无限排队。用户名仍只接受英文字母，密码仍只要求至少 6 个 Unicode 字符，不新增字符组合或复杂度规则。

每个请求总量、身份令牌桶、密码窗口最多分别保存 4,096 个状态条目，即每个服务实例合计最多 12,288 项；每个密码条目最多 8 个时间戳。用户名只在限额键中保存固定长度摘要。满表时拒绝新键，不驱逐尚有限额作用的旧键。每分钟最多做一次清理，只删除已空闲至少一分钟、并已完全补满的令牌桶；密码窗口在所有尝试均已过期后清除。耗尽的游客桶在一分钟后只有 30 个令牌，不会因清理凭空恢复为 60 个。

## 访客与重试语义

- 有效且尚未过期的服务器 Cookie 直接返回原 playerId；不创建玩家、不签发新 Cookie，也不消耗创建额度。仍受便宜请求的总量限制
- 没有 Cookie、伪造 Cookie、格式错误的单个 token、已失效/已过期 Cookie 均不能证明原身份，需要新游客额度。重复身份 Cookie 名称直接返回 400
- POST 正文解析和字段检查先于新游客准入，损坏 JSON、数组、客户端伪造权威字段和超限正文不会创建玩家或扣创建额度。已有的 8 KiB 正文上限、5 秒读取超时保持不变
- 正文读取期间可能发生退出、注册或到期；处理操作前重新读取身份，不能因为请求进入得早而得到已失效的身份
- HTTP 与冷 WebSocket 创建游客使用同一额度；不同入口不能各领一份额度。没有有效 Cookie 的并行首次请求各自可能创建一个游客，服务不能安全地把它们当作同一浏览器合并
- HTTP 限额返回 429、RATE_LIMIT 和向上取整的 Retry-After 秒数。密码队列满返回 429、PASSWORD_BUSY、Retry-After: 2。WebSocket 在升级前同样返回 429 和 Retry-After；浏览器 WebSocket API 不暴露此响应头，现有连接逻辑仍使用退避重连
- 现有网页显示“操作有些频繁，请稍后再试”。本改动未增加前端倒计时或自动密码重试

同一地址刚耗尽游客额度时，最早两秒后能再创建一位。整个服务的 180 个游客突发耗尽时，约 667 毫秒后补回一位，HTTP 的 Retry-After 为 1 秒。如果没有再消耗额度，地址桶两分钟后重新有 60 个。持续完全空闲两分钟后恢复完整突发，不代表任意一分钟只能或必定允许 60 人；初始一分钟的理论上限为 60 加期间补充的 30 位。

50 个冷访客占用 50 个新游客令牌，剩余 10 个。正常启动使用真实客户端模块测得每人 3 个 HTTP API 请求和 1 个 WS Upgrade：guest、curriculum、progress、ws，50 人共 200 次，小于 400 次地址突发。静态 JS/CSS/图片请求不进入此 API/WS 桶。此结论只覆盖受测启动流程；旧档导入、跨标签身份同步、网络重试会产生额外请求。

50 位访客可以依次或分组注册。注册后已经登录，不需要立即再登录一次；若紧接着集体进行第二轮密码操作，同一地址剩余的 10 个密码令牌不足以同时处理全部 50 人，应按 Retry-After 等待持续补充。50 个同时到达的真实 scrypt 操作也可能先耗尽 34 个在途位置，需要重试；增加 NAT 额度没有取消这个内存保护。

## 退出不能被新游客额度阻止

退出首先撤销当前账号会话，并关闭使用它的在线连接。若有未绑定的原游客 Cookie，则直接回到该游客。若需创建替代游客但额度不足，则成功返回 `{player:null}` 并清空账号 Cookie；原账号已退出，稍后可再申请游客。现有 IdentityClient 支持这个返回值，应用会尝试普通游客初始化；若仍限额则显示重试提示，不重新恢复已撤销账号。

请求总量或身份请求桶已经耗尽时，存在一个仅用于退出已验证账号的快捷分支。它仍要求有效 Host、POST、同源 Origin、JSON Content-Type、非重复 Cookie 及服务器可验证的账号 token。它只撤销这个账号会话，返回已有游客或 null，绝不会签发新玩家或新会话。此分支不读取或信任正文里的字段，而是丢弃正文；匿名请求和非法身份没有该豁免。普通额度内的退出仍校验空对象正文。

这项退出保证有一个边界：形状正确但伪造的账号 token，仍能在请求额度耗尽后触发一次简短的索引查询，以判断是否属于可退出账号。它不能签发或撤销真实身份，但不能声称所有数据库读取都受上述请求桶限制。公网流量控制仍需要在实际部署中另行评估。

## 代理与部署边界

地址只取 TCP socket.remoteAddress。客户端 X-Forwarded-For、Forwarded 等头无效，不存在默认信任代理或按任意转发头分配额度的开关。经过反向代理时，所有请求可能看起来来自同一个代理地址，因而共享 60 位游客突发和 30/分钟的地址补充；本改动不会悄悄放宽生产代理信任。

如需在反代后区分可信来源，必须另行设计并验证明确的代理地址、入口隔离、转发头覆写/清理与地址解析规则。本改动没有做这件事，没有设置网络权限、公开端口、凭据或部署。

限额是当前单实例进程内状态，重启会恢复桶，多个进程各有自己的桶，不是分布式限额或持久封禁。持续获准创建的游客仍会使 SQLite 增长；没有总玩家数上限、数据库容量保护或身份保留策略。本地同地址与多回环地址测试不能证明公网抗攻击、反代配置、移动弱网、TLS/WSS 或生产并发容量。
